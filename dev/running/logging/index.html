Logging

ropt reports its progress through Python's standard logging module. Switching it on takes one line and needs no code of your own. To collect what an optimization produces — to keep results, tabulate them, or stop it early — use result handlers instead.

Turning it on

Put this before the call to optimize:

import logging

logging.basicConfig(level=logging.INFO, format="%(name)s - %(levelname)s - %(message)s")

A short optimization over four realizations then reports:

ropt.running - INFO - Starting optimization
ropt.core - INFO - Function evaluation: 4/4 realizations succeeded
ropt.handlers - INFO - New best objective: 2
ropt.core - INFO - Gradient evaluation: 4/4 realizations succeeded
ropt.core - INFO - Function evaluation: 4/4 realizations succeeded
ropt.handlers - INFO - New best objective: 1.99886
ropt.core - INFO - Function evaluation: 4/4 realizations succeeded
ropt.handlers - INFO - New best objective: 1.50006
ropt.core - INFO - Stopping: Maximum number of function evaluations reached (3)
ropt.running - INFO - Optimization finished: MAX_FUNCTIONS_REACHED

Without that line ropt prints nothing at all: its output is discarded until an application adds a destination for it.

Reading the output

The per-batch counts appear one per batch of evaluations, and 4/4 means an ensemble of 4 evaluations came back with a value. While these keep arriving, the optimization is alive and calling your objective. A 3/4 after a series of 4/4 indicates a failed realization; how many failures an optimization tolerates is set by realization_min_success.

A new best objective is reported each time the optimization improves on what it had.

The reason for stopping is stated before the optimization ends, and the closing line names the ExitCode it finished with — the same one result.exit_code reports. See When something goes wrong for what each reason means.

The name at the start of each line identifies the part of ropt that produced it. That is what a bug report needs; leave %(name)s out of the format string if it is in the way.

Warnings only

INFO is one line per batch, which adds up on a long optimization. Setting the level to WARNING instead reports nothing while the optimization proceeds normally, and reports only events that did not stop it:

logging.basicConfig(level=logging.WARNING)

Typical examples are a scheduler that had to be queried twice, a cluster job that could not be cancelled and may still be running, a working directory kept behind so you can see what a failed job left, and evaluations that must finish before your program is allowed to exit. None of these raise, and most are reported nowhere else.

A failure that stops an optimization does not need logging to be seen: it either raises, or is named by the exit code the optimization ends with. See Troubleshooting.

Sending the output somewhere else

logging.basicConfig() writes to the console. To send ropt's output somewhere of its own — a file, a window, a queue — give the ropt logger a destination and stop its output from reaching the rest of your program's logging:

import logging

log_file = logging.FileHandler("optimization.log")
log_file.setFormatter(logging.Formatter("%(asctime)s %(levelname)s %(message)s"))

ropt_logger = logging.getLogger("ropt")
ropt_logger.setLevel(logging.INFO)
ropt_logger.addHandler(log_file)
ropt_logger.propagate = False

The last line is what separates ropt from the rest of your program. Without it, the output reaches this file and whatever the rest of your application does with logging — so if you also called logging.basicConfig(), every line appears twice.

While the optimizer is running

Setting stdout or stderr sends the optimizer's output to a file. In the parent process, capture is active while the backend runs and is released around each optimizer callback. Output from the callback, including the evaluation and ropt's callback logs, goes to the original streams.

The stream redirection is process-wide. While it is active, output from other threads can also end up in the capture file. This includes print(..., file=sys.stderr) and warnings.warn when they write to a redirected Python stream.

For backends that write from compiled code or a child process, ropt also redirects file descriptors 1 and 2. This applies to the SciPy method tnc and every external/ method. The descriptor redirection is process-wide too, so logging handlers created before the optimization, and other threads writing to those descriptors, can also write to the capture file.

To keep console logging on the original standard error when descriptor redirection is used, create the logging handler with a duplicate of descriptor 2 before the optimization:

import logging
import os

logging.basicConfig(stream=os.fdopen(os.dup(2), "w", buffering=1))

This applies only to messages sent through that handler. Other output from threads can still be captured.

Narrowing it down further

Every line comes from a logger named after the part of ropt that produced it, and all of them sit under ropt, which is why setting the level there covers the library. Setting it on one of the names below covers that part alone, which is the quickest way to follow a single mechanism: put ropt.executors at DEBUG to watch jobs being submitted without the per-batch traffic.

Logger Emits
ropt.running the start and finish of an optimization or evaluation, its configuration, and work-item dispatch
ropt.core per-batch realization counts, stopping conditions, optimizer callbacks, and reuse of cached results
ropt.executors executor start-up, job submission and cancellation, retained working directories, and exceptions raised by work that an aborted call no longer waits for
ropt.handlers each new best objective, and any handler that raised
ropt.backend.scipy, ropt.backend.external the method in use, and the external subprocess lifecycle
ropt.plugins plugin registration

DEBUG traces the mechanism: one line per optimizer callback, per dispatched batch and per cluster job, plus the configuration the optimization started from. It is verbose — a gradient-based method requests functions and gradients separately on most iterations, and each request is a line — but it is what to attach to a bug report.
