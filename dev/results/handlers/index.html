    Result Handlers

    An optimize call returns only the best result. A handler lets you collect or react to every result instead: it is an object that observes an optimization and processes its results as they arrive — keeping them, tabulating them, or invoking a callback.

    A handler is given Results objects — FunctionResults and GradientResults — which is what every other part of ropt provides too: a report callback receives one per evaluation, and optimize puts the best one on the results field of what it returns. Everything an optimization or evaluation produces is in them, at the field paths described in Working with Results, which is the vocabulary the handlers below are configured in.

    The report callback you may already be using is only shorthand for this: report= builds a handler for you behind the scenes, added to the optimization it is given to. One is built per optimization, each with a lock of its own, so the same callback given to optimizations that execute concurrently can be entered from several threads at once. A handler object given to those optimizations is entered by one at a time, because the lock belongs to the handler. A callback that accumulates across concurrent optimizations needs synchronization of its own.

    Attach handlers to an optimization with the handlers argument. The same handler can be passed to several optimize calls, accumulating the results of each in turn:

    from ropt import HistoryHandler, optimize

history = HistoryHandler()

optimize(config, x0, objective, handlers=[history])       # a single optimization
for x0 in start_points:                                   # ...or reused to
    optimize(config, x0, objective, handlers=[history])   # accumulate in turn

print(history.results)   # every result collected, across all the optimizations

    Handlers that store results expose them through handler["results"] (and, for HistoryHandler, the history.results shortcut).

    Sharing a handler across concurrent optimizations

    The same handler may also be given to optimizations that execute concurrently — those started together with Session.run, or ones you start on threads of your own. A handler's handle_event takes a lock around each call, so a second optimization waits for the first to finish rather than interleaving with it:

    from functools import partial

from ropt import HistoryHandler, session

history = HistoryHandler()
with session() as s:
    pool = s.thread_pool(workers=4)
    s.run(
        [
            partial(pool.optimize, config, x0, objective, handlers=[history])
            for x0 in start_points
        ]
    )

print(history.results)

    The results of the concurrent optimizations arrive interleaved, in an order that depends on which optimization reaches the handler first. Take the order from the results themselves — batch_id, or a metadata field you set per optimization — rather than from the order they arrive in.

    examples/handlers.py feeds two handlers from the same set of concurrent optimizations:

    with session() as s:
    optimize = partial(
        s.thread_pool(workers=len(STARTS)).optimize,
        CONFIG,
        handlers=[history, per_run],
    )
    s.run([partial(optimize, start, rosenbrock) for start in STARTS])

    Do not start an optimization from inside a handler that it can reach

    A handler is free to start an optimization of its own, but its own lock is held while it does. If that optimization lists the same handler, the handler is entered a second time. The outcome depends on the optimization the handler starts, not on the call that is feeding the handler. A nested optimize emits on the thread that called it — the one already inside the handler — so this raises a WorkflowError. A nested optimization started with Session.run emits on a thread that run started for it, which waits for a lock the first thread will not release until the optimization ends, and both stop. The same holds for two handlers that each start an optimization reaching the other. Give the inner optimization handlers of its own.

    Two handlers that write to the same external state are each serialized on their own, but not as a pair: one optimization can be inside the first while another is inside the second. Take a threading.Lock of your own inside both _handle_event implementations if they must not overlap.

    Built-in handlers

    The handlers below are exported from ropt, ready to use as they are.

    ResultsHandler

    ResultsHandler keeps a single result, read via handler["results"]:

    • what="best" (default) keeps the result with the lowest weighted objective seen so far; what="last" keeps the most recent valid result.
    • constraint_tolerance (optional) discards results that violate a constraint by more than the given tolerance.
    • filter (optional) is a callable that receives each Results and returns True to keep it or False to drop it.

    The gradient computed at the result it keeps, if there is one, is read via handler["gradient"]. A gradient usually reaches the handler in a later evaluation than that result, and is attached to it only if both of these hold:

    • GradientResults.uses returns True for the result, meaning the gradient was constructed from its values;
    • the gradient is at the same point as the result.

    In general the first does not imply the second. The stochastic gradient that ropt currently estimates is always at the point of the function evaluation it was constructed from, so for this gradient the second test always passes. handler["gradient"] is None while that gradient has not arrived, and stays None for a point where no gradient was computed — the best point of an optimization often is one.

    HistoryHandler

    HistoryHandler keeps every result it receives, in order, as a tuple. Read it with handler.results, which is an empty tuple until the first result arrives, or with handler["results"], the raw stored value, which is None until then.

    DataFrameHandler

    DataFrameHandler collects results into named DataFrames, using either polars (the default) or pandas as its engine; the corresponding package must be installed. Define a table with add_table(name, table_type, columns), where table_type is "functions" or "gradients" and columns maps result-field names (dotted attribute syntax) to column titles. The field names are those of the result objects, so variables and scaled.variables select different columns; see Working with Results. The runnable tables example defines tables of both types for the ensemble Rosenbrock function, and is explained below.

    from ropt import DataFrameHandler

tables = DataFrameHandler()
tables.add_table(
    "summary",
    "functions",
    {
        "batch_id": "Batch",
        "functions.objectives": "Objective",
        "variables": "Variable",
    },
)
optimize(config, x0, objective, handlers=[tables])
df = tables["summary"]

    Read one table with tables["summary"], or all of them with get_tables(). Columns appear in the order the specification lists them. A field whose value is a vector or matrix expands to several columns; the extra column levels come from the field's axis labels (or indices), joined to the title with a separator (, by default, set with sep=). The labels come from the names mapping: a length-2 variables gives Variable,v0 and Variable,v1 when the variables are named v0 and v1, and Variable,0 and Variable,1 when they are not. Because the column names follow results_to_pandas, both result-level and per-realization metadata can be included and renamed. The runnable metadata example shows a per-realization array with a configured names entry and exports it through evaluations.metadata.residual.

    Tables are built with polars by default. Pass engine="pandas" to get pandas DataFrames instead:

    tables = DataFrameHandler(engine="pandas")

    The tables carry the same columns under the same titles. As explained in Exporting to polars, polars has no index, so the key columns (batch_id, realization, and the other axis names) appear as ordinary leading columns rather than in the index; with pandas they form the index instead. Both engines align fields of differing granularity, broadcasting a per-batch field across the per-realization rows.

    Available fields

    The keys of the columns dict are taken from the two tables below. A "functions" table reads the fields of FunctionResults, a "gradients" table those of GradientResults. See What each field holds for the meaning of each field, and Scaling of results for the fields under scaled, which hold the same values in the domain the optimizer works in.

    Each variable, objective and constraint gets a column of its own, titled with its label from the names section, or with its index if it has no label. Each realization and each perturbation gets a row of its own. For example, this column dict:

    {
    "batch_id": "Batch",
    "realization": "Realization",
    "variables": "Variable",
    "evaluations.objectives": "Objective",
    "evaluations.constraints": "Constraint",
}

    gives the following table for the problem in the example below, with two variables named x and y, one unnamed objective, one constraint named limit, and five realizations:

    Batch Realization Variable,x Variable,y Objective,0 Constraint,limit
    0 0 -1.0 1.5 30.057 -7.371
    0 1 -1.0 1.5 27.263 -8.067
    0 2 -1.0 1.5 30.887 -10.147
    0 3 -1.0 1.5 28.286 -8.735
    0 4 -1.0 1.5 28.571 -9.656
    2 0 -2.0 -2.0 3816.174 -21.416

    A value that is the same for all realizations, such as variables, is repeated on each realization row. A gradient gets a column for each pair of function and variable, for example Objective gradient,0,x. batch_id, realization and perturbation are not read from the results: they identify the row, and appear only if they are listed. <key> in the tables below stands for a key of a metadata dict.

    A field that has no value in a result gives no columns, without an error. For example, functions.constraints gives no columns if no nonlinear constraints are configured, the realization weights give none without a realization filter, and constraint_info.linear_lower gives none without linear constraints. The exception is constraint_info as a whole: it exists only if all lower or all upper variable bounds are finite, or if linear or nonlinear constraints are configured. Without it, a table that lists a constraint_info or scaled.constraint_info entry raises a ValueError.

    Example: tables of both types

    The tables example optimizes the ensemble Rosenbrock function with variable bounds and a nonlinear constraint. The names section labels the variables and the constraint, and these labels are used in the column titles:

    CONFIG: dict[str, Any] = {
    "variables": {
        "variable_count": DIM,
        "perturbation_magnitudes": 1e-6,
        "lower_bounds": -2.0,
        "upper_bounds": 2.0,

    One handler holds all four tables. The second argument of add_table selects the results that fill the table:

    tables = DataFrameHandler()
tables.add_table("functions", "functions", FUNCTIONS)
tables.add_table("evaluations", "functions", EVALUATIONS)
tables.add_table("gradients", "gradients", GRADIENTS)
tables.add_table("perturbations", "gradients", PERTURBATIONS)

    The handler is passed to optimize, and the tables are read after it returns:

    optimize(CONFIG, INITIAL_VALUES, rosenbrock, handlers=[tables])
for name, table in tables.get_tables().items():
    print(f"{name}:\n{table}\n")

    The functions table has the columns Batch, Variable,x, Variable,y, Target objective, Objective,0, Constraint,limit and Violation,limit. The objective is not named in names, so its column uses the index 0.

    Other methods:

    • add_column(table, name, title) adds one column to an existing table.
    • set_callback(fn) calls fn(output_dir) whenever the tables are updated, where output_dir is the optimization's configured output_dir (None if it is not set).

    Write the tables to a file as they update

    set_callback fires on every update, so it is a convenient hook for saving the tables — to watch progress live or to write a final report. Pandas' to_string() gives aligned, human-readable columns with no extra dependencies; use to_csv() for machine-readable data, or to_markdown() if you have tabulate installed:

    def dump(output_dir):
    path = Path("progress.txt") if output_dir is None else output_dir / "progress.txt"
    with path.open("w") as fh:
        for name, df in tables.get_tables().items():
            fh.write(f"# {name}\n{df.to_string()}\n\n")

tables.set_callback(dump)
optimize(config, x0, objective, handlers=[tables])

    Because this writes to disk on every update, the optimization that emitted the result waits for the write to finish.

    Writing your own handler

    The built-in handlers above, and the report callback, cover the results an optimization produces. A handler of your own is for everything else: reacting to the start or the end of an optimization, writing results out in a format of your own, or keeping a summary that none of the built-ins keeps.

    Subclass EventHandler and implement two members:

    • event_types — the EnOptEventType values this handler wants to receive. An event of any other type never reaches it.
    • _handle_event(event) — called with each EnOptEvent of those types.
    from ropt.enums import EnOptEventType
from ropt.events import EnOptEvent
from ropt import EventHandler, optimize


class CountEvaluations(EventHandler):
    def __init__(self):
        super().__init__()
        self.count = 0

    @property
    def event_types(self):
        return {EnOptEventType.FINISHED_EVALUATION}

    def _handle_event(self, event: EnOptEvent) -> None:
        self.count += len(event.results)


counter = CountEvaluations()
optimize(config, x0, objective, handlers=[counter])
print(counter.count)

    An EnOptEvent carries the event_type that triggered it and a results tuple, which holds the Results objects of a FINISHED_EVALUATION and is empty for the other types. Its source is the compute step of the optimization that emitted the event, and calling event.source.stop() ends that optimization at the next evaluation boundary, with exit code STOPPED. The types an optimization emits are:

    Event type When it is emitted
    START_OPTIMIZER Just before the optimization algorithm begins iterating.
    FINISHED_OPTIMIZER After it finishes, whether it converged, stopped or failed.
    START_EVALUATION Before a batch of function or gradient evaluations.
    FINISHED_EVALUATION After that batch completes; carries its results.

    An evaluate or evaluate_batch task has no optimizer, and emits START_ENSEMBLE_EVALUATOR and FINISHED_ENSEMBLE_EVALUATOR around its single batch instead of the optimizer pair.

    Handlers are called on the thread that emits the event, in the order the handlers argument lists them, and the task waits until every handler for that event has returned. A handler that blocks therefore holds up the task that fed it, and any task waiting on the same handler's lock. Keep a handler shared by concurrent optimizations cheap; if one must do heavy I/O, buffer in memory and write once the optimizations have finished.

    A handler failure ends the task

    An exception raised by a handler is fatal. It is raised on the task's own stack, so it propagates as a single exception, and the handlers listed after it do not see that event.

    Read a handler's state after the tasks feeding it have finished

    State kept on a handler, or stored with handler[key], is deliberately not bound to a thread, so it can be read from anywhere once the tasks feeding it have returned. That return is what makes the latest values visible. Reading it while a task is still feeding the handler on another thread gives a valid but possibly stale value. To follow an optimization as it goes, use the handler's own _handle_event, or a report callback, rather than polling another handler's state.

    Handlers and separate processes

    On a thread pool (or with no pool) your objective and your handlers run in the same process and share memory: a handler can see anything the objective left behind — a global it set, a list it appended to, an object it mutated.

    A process or HPC pool breaks that. The objective runs in a separate worker process, while the optimizer, your handlers, and the rest of your program stay in the main process. They cannot share memory. The objective's only way to send information back is through what it returns — the objective and constraint values, and the result's metadata — all copied back to the main process:

    flowchart LR
    subgraph main["your main process"]
        opt["optimizer"]
        hand["handlers +<br/>your code"]
        opt --> hand
    end
    subgraph worker["worker process (process / local / HPC pool)"]
        obj["objective"]
    end
    opt -->|"variables"| obj
    obj -->|"result + metadata<br/>(copied back)"| opt
    How data is copied between processes

    To move work and results between processes, ropt serializes them — turns the objects into bytes and rebuilds them on the other side. Both a process pool and an HPC pool use Python's standard pickle by default, so an objective defined at module level works as is; a lambda, a closure, or a notebook-defined objective needs the optional cloudpickle extra. Most functions and data serialize fine, but things like open files, locks, or database connections may not.

    On a process pool the bytes travel over an in-machine channel. On an HPC pool they are written as files on a shared filesystem that the cluster nodes read, so it needs such a filesystem (its workdir).

    Serialization is only the mechanism ropt uses today; the essential requirement is that the data can be moved from one process to the other, so a future version could use a different transport — for example one that works over a network.

    Handlers see those returned results and nothing else. Anything the objective did only in memory — setting a module global, appending to a shared list, updating an object — happened inside the worker and is discarded when it finishes; your handlers and your main program never see it.

    Pools stay in the main process

    A pool is tied to the process that opened its session, so it is not usable in a worker. An objective that closes over one — to run work on it, or to start an inner optimization on it — is stopped in the worker, which reports the object by name. Do that work in the objective itself, or return what you need and act on it in the main process.

    So to get extra information from an evaluation to a handler (or to a later part of your program), return it instead of stashing it in shared state: attach it to the result's metadata (see Attaching metadata), which is returned with the result. Relying on shared state happens to work on a thread pool, but breaks the moment you switch to a process pool; returning the data works everywhere.
